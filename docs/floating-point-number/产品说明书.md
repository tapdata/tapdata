# TAP-12568 浮点数适配产品说明书

## 1. 产品目标

本版本将平台对数据源单精度、双精度二进制浮点数的描述从历史的统一 `TapNumber` 拆分为：

- `TapFloat`：默认对应 binary32，默认 metadata 为 32 bit、4 byte，有效十进制精度约 7 位。
- `TapDouble`：默认对应 binary64，默认 metadata 为 64 bit、8 byte，有效十进制精度约 15 位。
- `TapCoefficientFloat`：继承 `TapNumber` 的系数型中间声明；通过 mapping 中的 `coefficient` 有效位数区间解析为 `TapFloat` 或 `TapDouble`，不作为最终值 codec 类型。

本需求只处理 binary32/binary64，不改变 decimal、numeric、number、Decimal128、DECFLOAT 或其他定点/数值类型的语义。

## 2. 平台行为

### 2.1 类型与值承载

`TapFloat`、`TapDouble` 和 `TapCoefficientFloat` 都继承 `TapNumber`。`TapNumber` 仍表示全范围数值类型；是否使用浮点 codec 由具体类型决定，不能仅凭 `instanceof TapNumber` 把它们当成整数或定点数。

两个值对象均使用 `Double` 作为平台内部承载：

| 平台类型 | 内部值 | 入站行为 | 出站 Java 类型 |
| --- | --- | --- | --- |
| `TapFloat` / `TapFloatValue` | `Double` | 先按 `Float` 量化，再转回 `Double` | `Float` |
| `TapDouble` / `TapDoubleValue` | `Double` | 按 binary64 承载 | `Double` |

因此，平台不会因为 `TapFloat` 的内部承载而伪造超过 binary32 的有效精度；也不会让历史 `TapNumber` 的整数、定点行为发生改变。

### 2.2 schema 协议兼容

协议 byte 仍使用 `TYPE_NUMBER=8`，具体类型由 JSON 的 `typeName` 区分：

```json
{"type":8,"typeName":"TapFloat"}
{"type":8,"typeName":"TapDouble"}
{"type":8,"typeName":"TapCoefficientFloat"}
```

没有 `typeName` 的历史 `{"type":8}` 仍恢复为 `TapNumber`。`TapCoefficientFloat` 仅在 mapping 尚未完成解析的中间状态使用，正常完成 mapping 后 schema 应保存具体的 `TapFloat` 或 `TapDouble`。旧消费者忽略额外的 `typeName` 时仍可读取数值类别；要获得单双精度语义，消费者需要升级到支持本版本的 API/codec。

## 3. 数据源类型描述规则

新的实际 binary32/binary64 类型必须在 `spec.json` 的 `dataTypes` 中准确描述：

| 属性 | `TapFloat` | `TapDouble` |
| --- | ---: | ---: |
| `to` | `TapFloat` | `TapDouble` |
| `bit` | 32 | 64 |
| `storageBytes` | 4 | 8 |
| `effectivePrecision` | 7 | 15 |
| `fixed` | 缺省为 `false`；非空时按数据源配置保留 | 缺省为 `false`；非空时按数据源配置保留 |
| `precision`/`scale` | 不作为单双精度判定依据；若是源类型参数描述则按源语义保留 | 同左 |

`FLOAT(p)`、`float(n)` 等参数化源类型使用 `to=TapCoefficientFloat` 和 `coefficient` 区间，读取字段类型表达式中已有的有效位数参数 `p` 后选择最终类型。例如 SQL Server 的 `float(1..24)` 为 `TapFloat`，`float(25..53)` 为 `TapDouble`；MySQL 的边界为 `1..23` 和 `24..53`。这里的 `coefficient` 是 mapping 配置，不是 `TapNumber` 的属性，也不是新的源字段属性。spec 中的 `precision`/`scale` 若用于描述 `$precision`/`$scale` 的可取范围，仍属于源类型表达式参数，不会新增为类型对象属性。

MySQL/MariaDB 兼容类型中的 `FLOAT(M,D)`、`DOUBLE(M,D)` 的 M/D 是源端类型或显示语义，不作为平台 decimal `scale` 写入浮点类型。

## 4. 已覆盖的数据源修复

本次逐源完成 S-01～S-74：

- 覆盖两个连接器仓库的 76 个 spec 文件。
- 静态门禁检查 193 个浮点候选条目。
- 每个数据源分别核对官方类型定义、bit/byte、有效精度、范围、特殊值和参数语义。
- 实际 binary32/binary64 不再由新 spec 映射为 `TapNumber`。

以下类型不强行改为 `TapFloat`/`TapDouble`：

- Oracle `FLOAT(p)`：它是 `NUMBER` 子类型，继续使用 `TapNumber`。
- Elasticsearch `half_float`：16 bit，超出本需求范围。
- Elasticsearch `scaled_float`：scaled long，不是 binary32/binary64。
- Snowflake `DECFLOAT`：decimal floating point，超出本需求范围。
- Coding、HBase、Zoho 等没有足够实际 SDK/协议承载证据的逻辑类型：登记 source-file/type 级 allowlist，阻止仅凭名称推断宽度。

权威来源登记见 [floating-point-source-registry.json](./floating-point-source-registry.json)，异常和范围外类型见 [floating-point-spec-allowlist.json](./floating-point-spec-allowlist.json)。

## 5. 旧模型兼容

### 5.1 不需要重新加载模型

旧模型中浮点字段若仍保存为 `TapNumber`，源节点初始化时会使用当前连接器已经加载的 `DefaultExpressionMatchingMap` 在内存中解析：

1. 读取已持久化字段的 `dataType`/`pureDataType`。
2. 在已加载 source spec 中匹配具体类型和参数。
3. 解析成功后，仅修改本次运行内存中的 `TapField.tapType`。
4. 不访问源端 metadata，不重新加载模型定义，不回写旧模型。

例如旧的 SQL Server `float(53)` 会在运行时恢复为 `TapDouble`，旧的 `real` 会恢复为 `TapFloat`；字段中的小数值不会再因为 `TapNumber.scale=0` 被当成定点数截断。

### 5.2 无法唯一恢复时

如果旧字段只有模糊的 `TapNumber` 信息，且已加载 spec 不能唯一确定单双精度，解析器返回 `LEGACY_FLOAT_TYPE_UNRESOLVED`，不默认猜测为双精度。调用方必须在生成精度敏感目标类型、DDL 或其他类型敏感操作前处理该结果；普通历史数值搬运可以继续沿用 `TapNumber` 路径并记录告警。

旧模型已经丢失的二进制精度信息无法通过本版本恢复；本版本只恢复类型语义，不承诺恢复历史数据中已经发生的精度损失。

## 6. 使用和升级建议

1. 升级公共 API、引擎、管理端和相关 connector，使 `typeName`、`TapFloat`、`TapDouble` 和新 codec 同时可用。
2. 部署修正后的 connector spec；不需要批量重建旧模型。
3. 重新启动任务或让源节点重新初始化，使已加载的 source spec 参与旧字段的内存规范化。
4. 对自定义 connector，必须根据实际 Java/协议承载声明 `Float` 或 `Double`，不能仅使用展示名称推断。
5. 观察 `LEGACY_FLOAT_TYPE_UNRESOLVED` 和浮点降级告警；告警出现时补充 source spec 或人工确认字段类型，再执行类型敏感操作。

## 7. 风险与边界

- `TapFloat` 入站会执行 binary32 量化，这是设计要求，可能暴露原先以 `Double` 假装单精度时被掩盖的尾数差异。
- 双精度到单精度的目标映射可能丢失有效位，应由 mapping/目标类型策略显式处理，不能静默降级。
- 未升级的旧消费者只能看到 `TYPE_NUMBER`，可能丢失单双精度展示语义；数据值仍可按旧数值路径读取。
- NaN/Infinity 是否保留由数据源和目标类型能力决定，不能由 spec 名称推断。
- 本需求不改变 decimal/number 的精确数值处理，也不把 Oracle `FLOAT(p)` 等十进制语义类型误改为二进制浮点。

## 8. 源属性与默认值

`TapFloat`、`TapDouble` 的 `bit`、`storageBytes`、`effectivePrecision`、`fixed` 等属性遵循“数据源配置优先、缺省值兜底”规则：

- source spec 显式提供非空值时，框架原样保留，不在 setter 中强制改成 32/64、4/8 或 false。
- source spec 未提供或值为 null 时，`TapFloat` 默认使用 32/4/7/false，`TapDouble` 默认使用 64/8/15/false。
- `TapCoefficientFloat` 的 `coefficient` 不进入类型对象，只用于按有效位数选择具体浮点类型。
