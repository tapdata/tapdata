# 浮点数单/双精度适配详细设计

> 本文基于 [设计概要.md](/Users/gavinxiao/kit/tapdata/tapdata/docs/floating-point-number/设计概要.md)，将 TAP-12568 的设计原则固化为可直接分工、编码、测试和验收的实现方案。

## 1. 设计结论

本方案一次性完成平台类型、值对象、codec、mapping、schema 序列化、历史模型兼容和连接器 spec 修复，不设置依赖后续阶段的功能尾项。

最终采用以下硬约束：

1. `TapFloat`、`TapDouble` 和 `TapCoefficientFloat` 都是 `TapNumber` 的具体扩展类型；`TapCoefficientFloat` 只作为由系数选择最终精度的中间声明类型，最终值类型必须解析为 `TapFloat` 或 `TapDouble`。
2. `TapCoefficientFloat` 的 `coefficient` 是 mapping 配置元数据，不是 `TapNumber`、`TapFloat` 或 `TapDouble` 的字段；不新增 `TapFloatingPoint` 作为新的业务 schema 类型。
3. `TapFloatValue`、`TapDoubleValue` 是 `TapValue` 下的直接业务值类型，二者的 Java 底层值都为 `Double`。
4. `TapFloatValue` 写入前必须经过 `Float` binary32 量化；`TapDoubleValue` 按 binary64 保存。
5. `TYPE_NUMBER=8` 保留，作为协议数值类别；具体业务类型通过 `typeName` 区分，Java 继承关系不再承担类型区分职责。
6. 新发现的实际 binary32 类型使用 `TapFloat`，实际 binary64 类型使用 `TapDouble`；新 spec 不得再将实际单双精度浮点数映射到 `TapNumber`。
7. 旧模型只有 `tapType=TapNumber` 时，先用已有连接器身份、`dataType`、`pureDataType` 和本地修复后 spec 尝试内存规范化；不能确定时保留旧路径，不猜测。
8. 数据源 64 位类型误标为单精度是必须修复的 spec/编码缺陷，不能通过兼容分支掩盖。
9. `TapNumber.precision/scale` 不能被用来推断二进制浮点的单双精度或平台 decimal 语义；source spec 中已有的 `precision/scale` 可以继续描述源类型表达式参数。浮点系数型字段使用已有有效位数参数和 `coefficient` 区间选择最终类型，不增加新的 coefficient 属性到 `TapNumber`。

## 2. 范围、非目标和验收结果

### 2.1 本次范围

- `tapdata-common-lib` 中公共 `TapType`、`TapValue`、codec、mapping 和 Java 类型推导。
- `tapdata` 中 schema JSON 读写、引擎 codec 分派、模型推演、DDL 生成和历史模型入口。
- `tapdata-connectors` 与 `tapdata-connectors-enterprise` 中 `src/main/resources` 下的浮点 spec。
- 连接器 spec 静态检查、官方依据登记和回归测试。

### 2.2 非目标

- 不改造 `DECIMAL`、`NUMBER`、`NUMERIC`、`MONEY` 或其他精确数值模型。
- 不引入任意精度浮点类型。
- 不在本需求内新增 `Decimal128`、Elasticsearch `scaled_float`/`half_float`、Snowflake `DECFLOAT`、Oracle `FLOAT(p)` 的二进制浮点语义。
- 不恢复历史链路中已经被截断的小数值；类型规范化只能修复后续处理。

### 2.3 完成判定

必须同时满足：

- 公共 API 可以创建、克隆、序列化和反序列化 `TapFloat`/`TapDouble`。
- `Float`、`Double`、`BigDecimal` 的 Java 推导分别得到 `TapFloat`、`TapDouble`、`TapNumber`。
- 旧 JSON 无 `typeName` 仍恢复 `TapNumber`；新 JSON 带 `typeName` 恢复具体浮点类型。
- 新发现实际单精度/双精度的所有 spec 条目分别输出 `TapFloat`/`TapDouble`。
- SQL Server `float(53)` 推演为 `TapDouble`，再映射 StarRocks `DOUBLE`，不能变成 `decimal(27,0)`。
- 历史模型不重新访问源端、不重新加载模型定义即可继续运行；无法唯一判断时保留旧行为并给出结构化状态。
- 浮点 codec 不再通过 `scale` 或固定的 `bit` 值猜测类型；最终精度由具体 `TapType` 或 `TapCoefficientFloatMapping` 的系数规则决定。

## 3. 现状代码和改造边界

| 模块 | 当前入口 | 当前问题 | 本方案改造 |
| --- | --- | --- | --- |
| 公共类型 | `TapType.java`、`TapNumber.java` | `TYPE_NUMBER` 只能恢复 `TapNumber`；`TapNumber` 同时承载整数、定点和浮点 | 增加 `TapFloat`/`TapDouble`；保留 `TYPE_NUMBER=8`；按 `typeName` 恢复 |
| 值对象 | `TapNumberValue.java` | 所有浮点值都变成旧 `TapNumberValue` | 增加两个独立值对象，均为 `Double` 载体 |
| 入站 codec | `ToTapNumberCodec.java` | `Number -> String -> Double`，且不区分 binary32/binary64 | 新增单、双精度 codec；旧 codec 只服务 `TapNumber` |
| 出站 codec | `FromTapNumberCodec.java` | 依据 `scale` 和 `bit` 推断返回 `Float` 或 `Double` | `TapFloatValue` 固定返回 `Float`，`TapDoubleValue` 固定返回 `Double` |
| mapping | `TapNumberMapping.java` | 浮点的 `precision/scale` 进入定点匹配 | 增加浮点 mapping；`TapNumberMapping` 排除新浮点类型 |
| mapping 构造 | `TapMapping.java` | mapping 实现类只能由 `to` 字段推导 | 支持可选 `mapping` 字段，使参数化 `float(p)` 可返回两个具体类型 |
| Java 推导 | `JavaTypesToTapTypes.java` | `Float`/`Double` 都生成带 scale 的 `TapNumber` | `Float -> TapFloat`、`Double -> TapDouble` |
| codec 分派 | `TapCodecsFilterManager.java`、`TapCodecsFilterManagerSchemaEnforced.java` | `TYPE_NUMBER` 不直接从 schema 取得具体 codec | 按具体 `TapType` 调用 `toTapValueCodec()` |
| JSON 读写 | `iengine-common/JSONUtil.java`、`tm-common/JsonUtil.java` | 只看数值 `type`，无法恢复具体浮点 | `typeName` 优先，旧 `type=8` 兜底 |
| PDK 读写 | `TapConstants.java` | Fastjson detector 只按 `type=8` 恢复 `TapNumber` | 增加 `typeName` detector，保持数字 type 兼容 |
| 引擎/管理端 | `ProcessNodeSchemaUtil`、`DiscoveryServiceImpl`、`CompareRecord`、预览节点等 | `instanceof TapNumber` 和 `TYPE_NUMBER` 语义混用 | 拆分“数值类别判断”和“旧整数/定点判断” |
| 连接器 spec | 两个连接器仓库的 `src/main/resources` | 约 76 个候选 spec 文件仍有浮点 `to=TapNumber` 或属性错误 | 每个数据源单独核对官方定义并修复 |

当前代码基线为 Java 8/11/17 多版本构建，因此新增公共 API 必须使用 Java 8 可编译语法，不能使用 record、sealed class 等高版本语法。

## 4. 公共类型设计

### 4.1 类型层次

固定为：

~~~text
TapType
└── TapNumber
    ├── TapFloat
    ├── TapDouble
    └── TapCoefficientFloat
~~~

`TapNumber` 是平台的全范围数值类型，不只表示普通整数或定点数。浮点专有字段和 codec 仍由 `TapFloat`/`TapDouble` 提供；`TapCoefficientFloat` 只承载兼容 `TapNumber` 属性并在 mapping 阶段解析为具体浮点类型。`coefficient` 不进入类型对象。

### 4.2 `TapFloat` 和 `TapDouble` 的字段

两个类均继承 `TapNumber`，字段定义保持相同结构，但默认值不同：

| 字段 | 类型 | `TapFloat` 默认值 | `TapDouble` 默认值 | 约束 |
| --- | --- | --- | --- | --- |
| `type` | `byte` | `TYPE_NUMBER` | `TYPE_NUMBER` | 永远为 8 |
| `bit` | `Integer` | 32 | 64 | 非空时以数据源配置为准；不能在框架 setter 中强制固定 |
| `storageBytes` | `Integer` | 4 | 8 | 非空时以数据源配置为准；缺省时使用默认值 |
| `effectivePrecision` | `Integer` | 7 | 15 | 默认能力描述；source spec 非空值优先，不参与 DECIMAL 推导 |
| `binaryPrecision` | `Integer` | 源端有 `p` 时保留 | 源端有 `p` 时保留 | 仅表示二进制 precision |
| `minValue` | `BigDecimal` | 有限值最小边界 | 有限值最小边界 | 不写入 Infinity |
| `maxValue` | `BigDecimal` | 有限值最大边界 | 有限值最大边界 | 不写入 Infinity |
| `fixed` | `Boolean` | `false` | `false` | 非空时以数据源配置为准；缺省时为 false |
| `supportsNaN` | `Boolean` | 按数据源 | 按数据源 | 不因 IEEE 754 默认支持而强行开启 |
| `supportsInfinity` | `Boolean` | 按数据源 | 按数据源 | 同上 |

实现要求：

- 增加 `get/set` 和链式 setter，命名与 `TapNumber` 现有风格一致。
- 构造函数设置 `type`、`bit`、`storageBytes`、`fixed` 和默认范围。
- `cloneTapType()` 必须返回具体类，不得返回 `TapNumber`。
- `tapValueClass()` 分别返回 `TapFloatValue.class`、`TapDoubleValue.class`。
- `toTapValueCodec()` 分别返回 `TapDefaultCodecs.TAP_FLOAT_VALUE`、`TapDefaultCodecs.TAP_DOUBLE_VALUE`。
- `bit`、`storageBytes`、`effectivePrecision`、`fixed` 的非空值必须保留；只有 null/缺省时才使用具体类型默认值。不能在框架层把数据源属性值限制为 32/64/4/8 或 false。
- `TapFloat`/`TapDouble` 的具体 codec 由 Java 类型决定；`bit` 是可携带的源端元数据，不是 setter 的硬约束。
- `TapCoefficientFloat` 继承 `TapNumber` 的通用属性，但不增加 `coefficient` 字段。

建议的类签名：

~~~java
public class TapFloat extends TapNumber {
    public TapFloat() { /* set type and binary32 defaults */ }

    @Override
    public TapType cloneTapType() { /* return TapFloat */ }

    @Override
    public Class<? extends TapValue<?, ?>> tapValueClass() {
        return TapFloatValue.class;
    }

    @Override
    public ToTapValueCodec<?> toTapValueCodec() {
        return InstanceFactory.instance(
            ToTapValueCodec.class,
            TapDefaultCodecs.TAP_FLOAT_VALUE
        );
    }
}
~~~

`TapDouble` 与上述接口相同，仅替换为 binary64 和 `TapDoubleValue`。

### 4.3 `TapType` 兼容扩展

在 `TapType.java` 中：

1. `getTapTypeClass(byte)` 的 `TYPE_NUMBER` 分支继续返回 `TapNumber.class`，保证旧 numeric-only payload 可读。
2. `getTapTypeClass(String)` 支持 `TapFloat`、`TapDouble`、`TapCoefficientFloat`。
3. 增加只读 `getTypeName()`，返回 `getClass().getSimpleName()`，供新 schema 写入 `typeName`。
4. `TapFloat`、`TapDouble`、`TapCoefficientFloat` 的 `getType()` 仍返回 8。
5. 不增加新的 `TYPE_FLOAT`/`TYPE_DOUBLE` byte，避免历史协议和过滤器失效。

## 5. 值对象和 codec 设计

### 5.1 值对象

新增：

- `io.tapdata.entity.schema.value.TapFloatValue extends AbsBasicTapValue<Double, TapFloat>`
- `io.tapdata.entity.schema.value.TapDoubleValue extends AbsBasicTapValue<Double, TapDouble>`

两个类都提供：

~~~java
public TapFloatValue() {}
public TapFloatValue(Double value) {}
public TapType createDefaultTapType() {}
public Class<? extends TapType> tapTypeClass() {}
~~~

`TapFloatValue` 的约束：

- `value` 的实际 `Double` 必须是某个 `Float` 值经过 widening 得到的结果。
- 构造器和 codec 都不得直接保存未经量化的任意 `Double`。
- `1.234567890123` 进入 `TapFloatValue` 时按 `Float.parseFloat`/`floatValue` 量化，再保存为 `Double`。

`TapDoubleValue` 的约束：

- `value` 是 binary64 `Double`。
- 不执行额外的 binary32 量化。
- `Float` 输入若明确目标类型为 `TapDouble`，先 widening 为 `Double`，不回溯恢复丢失的精度。

不继承 `TapNumberValue`，不通过 `TapNumberValue<Double>` 加字段标识浮点类型。

### 5.2 入站转换规则

新增：

- `ToTapFloatCodec implements ToTapValueCodec<TapFloatValue>`
- `ToTapDoubleCodec implements ToTapValueCodec<TapDoubleValue>`

规则如下：

| 输入 | `ToTapFloatCodec` | `ToTapDoubleCodec` |
| --- | --- | --- |
| `Float` | `Float.floatValue()` 后转 `Double` | 转 `Double` |
| `Double` | `floatValue()` 后转 `Double` | 原值转 `Double` |
| `BigDecimal` | `floatValue()` 后转 `Double` | `doubleValue()` 后转 `Double` |
| 其他 `Number` | 先转 `floatValue()` | 先转 `doubleValue()` |
| `String/CharSequence` | `Float.parseFloat` 后转 `Double` | `Double.parseDouble` |
| `Boolean` | 延续旧 codec：true=1.0、false=0.0 | 同上 |
| null | 返回 null | 返回 null |
| 非数值对象 | 返回 null 并记录 codec debug 日志 | 返回 null 并记录 codec debug 日志 |

特殊值：

- 输入为 NaN/Infinity 且目标 `TapType` 对应能力为 true：保留特殊值。
- 输入为 NaN/Infinity 且目标能力为 false：返回 null，并使用结构化 codec 错误；不得悄悄转成最大有限值。
- 数值超出 `Float` 有限范围但未声明 Infinity 能力：返回转换失败；不能把 Java `Float.POSITIVE_INFINITY` 当成普通范围值。

`ToTapNumberCodec` 保持旧实现可读性，但新浮点 `TapType` 不得再调用它。

### 5.3 出站转换规则

新增：

- `FromTapFloatCodec implements FromTapValueCodec<TapFloatValue>`
- `FromTapDoubleCodec implements FromTapValueCodec<TapDoubleValue>`

固定返回：

| 值对象 | Java/JDBC 出站类型 |
| --- | --- |
| `TapFloatValue` | `Float` |
| `TapDoubleValue` | `Double` |
| `TapNumberValue` | 按旧 codec 逻辑返回整数、`BigDecimal` 或 `Double` |

删除浮点类型判断中的以下逻辑：

~~~java
scale != 0 && bit == 32
~~~

新 codec 只依据值对象和具体 `TapType` 分派。`FromTapNumberCodec` 遇到非 `TapNumber` 的值对象不负责转换。

### 5.4 codec 注册和分派

在 `TapDefaultCodecs.java` 中：

- 增加常量 `TAP_FLOAT_VALUE`、`TAP_DOUBLE_VALUE`。
- `classFromTapValueCodecMap` 注册两个出站 codec。
- 不用“原始 Java 类 -> codec”区分 `Float` 和 `Double` 的 schema 语义；schema 存在时以 `TapType.toTapValueCodec()` 为准。
- 无 schema 的新字段先通过 `JavaTypesToTapTypes.toTapType(value)` 得到具体类型，再调用该类型的 codec。

在 `TapCodecsFilterManager.java` 和 `TapCodecsFilterManagerSchemaEnforced.java` 中：

1. `getValueCodec(TapType)` 对 `TYPE_NUMBER` 直接返回 `typeFromSchema.toTapValueCodec()`。
2. schema 明确为 `TapFloat`/`TapDouble` 时，必须使用对应 codec。
3. schema 缺失时，先由 Java 实际值推导类型，再选择对应 codec。
4. `TYPE_NUMBER` 的“是 Number”校验保留；具体单/双精度校验由 codec 负责。
5. `TapValue` 已存在时不重新包装，避免旧缓存值被重复量化。

## 6. Java 类型推导

修改 `JavaTypesToTapTypes.java`：

- `Float`/`float -> TapFloat`
- `Double`/`double -> TapDouble`
- `BigDecimal -> TapNumber` 精确语义
- `Long`、`Integer`、`Short`、`Byte` -> 现有 `TapNumber`
- 其他 `Number` -> 现有兼容行为，默认 `TapNumber`
- `toTapType(Class)` 增加 `TapFloat.class`、`TapDouble.class`
- 不再为 Java `Float`/`Double` 设置 `TapNumber.scale`、`TapNumber.precision`

推导顺序必须先判断 `Float`、`Double`、`BigDecimal`，再判断 `Number`，防止被兜底分支吞掉。

## 7. mapping 设计

### 7.1 静态浮点 mapping

新增：

- `io.tapdata.entity.mapping.type.TapFloatMapping`
- `io.tapdata.entity.mapping.type.TapDoubleMapping`

静态 spec 示例：

~~~json
{
  "float": {
    "to": "TapFloat",
    "bit": 32,
    "storageBytes": 4,
    "effectivePrecision": 7,
    "value": ["-3.402823466E+38", "3.402823466E+38"],
    "fixed": false,
    "supportsNaN": true,
    "supportsInfinity": true
  },
  "double": {
    "to": "TapDouble",
    "bit": 64,
    "storageBytes": 8,
    "effectivePrecision": 15,
    "value": ["-1.7976931348623157E+308", "1.7976931348623157E+308"],
    "fixed": false,
    "supportsNaN": true,
    "supportsInfinity": true
  }
}
~~~

`TapFloatMapping.toTapType` 只返回 `TapFloat`，`TapDoubleMapping.toTapType` 只返回 `TapDouble`。两者的 `matchingScore` 只接受对应具体类型，遇到其他类型返回 `TapMapping.MIN_SCORE`。

### 7.2 由有效位数系数选择精度的 mapping

对于源类型本身不是固定单精度/双精度，而是由字段类型中的有效位数参数 `p` 决定精度的场景，`spec.json` 只需要把 `to` 设置为 `TapCoefficientFloat`，并声明系数到具体类型的区间映射：

~~~json
{
  "float($precision)": {
    "to": "TapCoefficientFloat",
    "coefficient": {
      "TapFloat": [1, 23],
      "TapDouble": [24, 53]
    },
    "precision": [1, 53],
    "fixed": false
  }
}
~~~

这里的 `precision` 是源类型表达式已有的 `$precision` 参数描述，`p` 的实际值由连接器解析后放入 mapping 参数；`coefficient` 是 mapping 配置，不是 `TapNumber` 的新属性，也不是需要额外写入字段 metadata 的属性。系数的业务含义是数据源定义的浮点有效位数，具体边界必须以对应数据源官方定义为准。

`TapMapping.build` 根据 `to=TapCoefficientFloat` 选择 `TapCoefficientFloatMapping`。核心算法：

~~~text
输入 dataType 和已解析的 params
  ├─ 读取 params["precision"]，即字段类型中的有效位数 p
  ├─ 没有 p 时按该 source mapping 已有的默认/优选 precision 规则处理
  ├─ 在 coefficient 的不重叠区间中查找 p
  ├─ 命中 TapFloat 区间：创建 TapFloat，并继续应用 source 配置
  └─ 命中 TapDouble 区间：创建 TapDouble，并继续应用 source 配置
~~~

实现要求：

- `coefficient` 必须存在，且只能声明 `TapFloat`、`TapDouble` 的有效位数区间。
- 区间不能反向或重叠；缺失系数、缺失 p、p 超出区间属于 mapping 配置错误。
- 选出具体类型后，`bit`、`storageBytes`、`effectivePrecision`、`fixed` 等非空 source 属性必须原样保留；未设置时由 `TapFloat`/`TapDouble` 使用默认值。
- 不得把 `p` 拼成新的 source 类型属性，也不得把 `coefficient` 注入 `TapNumber`、`TapFloat` 或 `TapDouble`。
- 旧的 `TapFloatingPointMapping` API 如仍被历史 spec 使用必须保留兼容，但不作为这类字段的新 spec 声明方式。

边界示例：

- MySQL/MariaDB `FLOAT(p)`：按官方边界使用 `1..23 -> TapFloat`、`24..53 -> TapDouble`。
- SQL Server/PostgreSQL/DB2 等 `FLOAT(p)`：按官方边界使用 `1..24 -> TapFloat`、`25..53 -> TapDouble`。
- Sybase 等数据源如果官方范围为 `1..15`/`16..48`，必须使用该数据源自己的区间，不能套用其他数据库边界。
- MySQL `FLOAT(M,D)` 的 `M,D` 是源端显示/约束语义，不等同于本节的有效位数系数，不能据此新增 `coefficient` 参数。

### 7.3 mapping 匹配规则

`TapNumberMapping` 修改为：

- `matchingScore` 和 `fromTapType` 只接受 `TapNumber`、`TapMoney`。
- `TapFloat`/`TapDouble` 不再进入旧 `TapNumberMapping`。
- 精确数值到浮点的转换必须由浮点 mapping 显式支持；默认不从 `TapNumber.scale` 推断浮点。
- `TapFloatMapping` 不匹配 `TapDouble`。
- `TapDoubleMapping` 可以匹配 `TapFloat` 的安全 widening，但生成目标类型时仍必须明确输出 `Double`。
- `TapDouble` 到 `TapFloat` 默认返回 warning 或失败结果，不允许无提示降精度。

## 8. schema 序列化和反序列化

### 8.1 新 schema 格式

新版本序列化的浮点字段至少包含：

~~~json
{
  "type": 8,
  "typeName": "TapDouble",
  "bit": 64,
  "storageBytes": 8,
  "effectivePrecision": 15,
  "fixed": false,
  "minValue": "-1.7976931348623157E+308",
  "maxValue": "1.7976931348623157E+308",
  "supportsNaN": true,
  "supportsInfinity": true
}
~~~

`typeName` 对所有新版本 `TapType` 可统一输出；旧消费者会忽略未知字段。读取时按 `typeName` 恢复合法具体类，包括 `TapCoefficientFloat`；但 mapping 完成后的最终 schema 不应把中间声明保留为值 codec 类型。

### 8.2 反序列化优先级

所有反序列化入口统一执行：

~~~text
typeName 存在
  ├─ TapFloat -> TapFloat
  ├─ TapDouble -> TapDouble
  ├─ TapCoefficientFloat -> TapCoefficientFloat
  ├─ TapNumber -> TapNumber
  └─ 其他合法业务类型 -> TapType.getTapTypeClass(typeName)
typeName 不存在
  └─ 按 numeric type 读取；type=8 -> TapNumber
~~~

必须修改：

- `tapdata/iengine/iengine-common/.../JSONUtil.java`
- `tapdata/manager/tm-common/.../JsonUtil.java`
- `tapdata-common-lib/plugin-kit/tapdata-pdk-runner/.../TapConstants.java`

处理规则：

- `typeName` 与 `type` 冲突时，以 `typeName` 为准，但记录 schema warning；若 `typeName` 不合法则失败，不静默回退。
- 缺失 `typeName` 的历史 `type=8` 继续恢复 `TapNumber`。
- 浮点 `minValue/maxValue` 的 JSON 字符串转换为 `BigDecimal`；不能将 Infinity 解析成 `BigDecimal`。
- 旧 `TapNumber` 的 Infinity 兼容处理保留在旧分支，不影响新浮点分支。

### 8.3 PDK 和旧服务兼容

- `TapConstants.abstractClassDetectors` 增加基于 `typeName` 的 `TapFloat`/`TapDouble` detector，并放在 numeric `TYPE_NUMBER` detector 之前。
- 老服务只识别 `type=8` 时会恢复为 `TapNumber`，这是已知兼容退化；新语义生效前，相关 schema 消费端必须升级。
- 不改变 `TYPE_NUMBER` 数字值，不新增协议 byte。

## 9. 历史模型兼容设计

### 9.1 解析对象

在 `tapdata-common-lib/plugin-kit/tapdata-api` 新增：

- `io.tapdata.entity.schema.compat.LegacyTapTypeResolver`
- `io.tapdata.entity.schema.compat.LegacyTapTypeResolution`

采用 Java 8 兼容的普通类和 enum，不使用 record。

建议接口：

~~~java
public class LegacyTapTypeResolver {
    public LegacyTapTypeResolution resolve(
        String connectorId,
        TapField field,
        Map<String, Object> sourceSpec
    );
}

public class LegacyTapTypeResolution {
    public enum Status {
        EXPLICIT_NEW_TYPE,
        NORMALIZED_TO_FLOAT,
        NORMALIZED_TO_DOUBLE,
        LEGACY_UNCHANGED,
        UNRESOLVED
    }

    private TapType tapType;
    private Status status;
    private String reason;
    private boolean typeSensitiveOperationBlocked;
}
~~~

### 9.2 解析优先级

~~~text
当前 tapType 是 TapFloat/TapDouble
  -> 原样保留，不重复推断

当前 tapType 是 TapNumber
  -> 连接器身份 + dataType/pureDataType + 本地修复 spec 唯一匹配
       -> 内存转换为 TapFloat/TapDouble
  -> 缺少连接器/源类型/匹配结果不唯一
       -> 保持 TapNumber，状态 LEGACY_UNCHANGED 或 UNRESOLVED

当前 tapType 缺失
  -> 不能从空值猜测；交给原有 schema 补全流程
~~~

禁止使用以下旧属性单独推断：

- `TapNumber.bit`
- `TapNumber.precision`
- `TapNumber.scale`
- `TapNumber.fixed`
- `TapNumber.minValue/maxValue`

这些字段无法可靠区分“源端实际 binary32/binary64”和“旧 mapping 错误生成的定点元数据”。

### 9.3 调用边界

`LegacyTapTypeResolver` 不能放在只有 JSON 的反序列化器中，因为 JSON 入口没有连接器身份。调用边界为“模型字段已经装载、连接器上下文已知、进入类型推演/codec/DDL 前”：

1. 模型/任务装载 `TapTable` 后，遍历 `nameFieldMap`。
2. 取连接器 id、字段 `dataType`、`pureDataType`、当前 `tapType` 和本地 `DefaultExpressionMatchingMap`。
3. 规范化每个字段一次，并将结果缓存到本次运行的 `TapTable`/字段上下文。
4. 后续 mapping、codec、DDL、schema union 只能读取规范化后的字段类型。
5. 不回写数据库中的历史 schema；只有用户显式保存迁移结果时才写出 `typeName`。

实现接入点必须覆盖：

- `LoadSchemaRunner`/`DiscoverSchemaService` 的字段类型补全入口。
- 引擎 `HazelcastSourcePdkBaseNode` 进入 codec 前的 schema 入口。
- 管理端目标类型推演和 DDL 生成入口。
- 预览节点、schema union 和 compare/inspect 等再次进行类型判断的入口。

### 9.4 无法解析时的行为

- 普通数据搬运：保留 `TapNumber`，继续旧 codec/mapping 路径，写结构化告警。
- 需要生成新目标 DDL、判断单/双精度或进行精度敏感转换：返回 `LEGACY_FLOAT_TYPE_UNRESOLVED`，阻止静默决策。
- 不允许通过“默认 TapDouble”解决歧义；这会把错误隐藏到目标 schema。
- 历史缓存仍为 `TapNumberValue` 时，可在字段已规范化后显式转换为 `TapFloatValue`/`TapDoubleValue`；已丢失的精度不可恢复。

## 11. spec.json 统一契约和数据源规则

### 11.1 统一字段契约

普通浮点条目必须满足：

- 固定类型使用 `to=TapFloat` 或 `to=TapDouble`；由有效位数系数选择精度的类型使用 `to=TapCoefficientFloat`，并声明 `coefficient`。
- `bit`、`storageBytes`、`effectivePrecision`、`fixed` 等字段如果由数据源配置，则以数据源配置为准；缺省时才使用具体类型默认值。
- `TapFloat`/`TapDouble` 的默认值分别为 32/4 和 64/8，但这些默认值不是对数据源配置的强制限制。
- `precision`、`scale` 等已有字段只有在源类型表达式或 mapping 解析确实需要时才保留；不能把有效位数系数新增为 `TapNumber` 属性，也不能把它当作 decimal scale。
- `value` 使用字符串边界，避免 JSON/Java 二次舍入。
- `specialValues`、`supportsNaN`、`supportsInfinity` 只按源端官方能力填写。
- 实际源类型必须有官方文档、协议或 SDK 类型依据。

### 11.2 已确定的来源规则

| 来源家族 | 具体规则 |
| --- | --- |
| MySQL/MariaDB/TiDB/OceanBase MySQL/PolarDB MySQL/ADB MySQL/RDS MySQL/PXC/TDSQL MySQL/GBase 8a | `FLOAT` 为 32 bit；`DOUBLE`、`REAL`、`DOUBLE PRECISION` 为 64 bit；MySQL `FLOAT(p)` 按 1–23 单精度、24–53 双精度；`FLOAT(M,D)` 的 M/D 不写入平台 scale |
| PostgreSQL/Greenplum/HighGo/openGauss/PolarDB PostgreSQL/Kingbase/Vastbase/DWS/RisingWave | `real`/`float4` 为 32 bit；`double precision`/`float8` 为 64 bit；`float(p)` 按 1–24/25–53 分流，默认双精度 |
| SQL Server/ApsaraDB RDS SQL Server/TencentDB SQL Server | `real` = `float(24)` = 32 bit；`float(n)` 1–24 为 `TapFloat`，25–53 为 `TapDouble`，默认 53；不能把 `float(53)` 标为单精度 |
| Oracle/OceanBase Oracle | `BINARY_FLOAT` -> `TapFloat`；`BINARY_DOUBLE` -> `TapDouble`；Oracle `FLOAT(p)` 是 `NUMBER` 子类型，保留 `TapNumber`，不得按名称归为二进制浮点 |
| StarRocks/Doris/SelectDB | `FLOAT`/`REAL` 为 32 bit；`DOUBLE`/`FLOAT8`/`DOUBLE PRECISION` 为 64 bit；不填 scale |
| ClickHouse | `Float32` -> `TapFloat`，`Float64` -> `TapDouble`；官方忽略的类型参数不进入 precision/scale |
| BigQuery | `FLOAT64` -> `TapDouble`；删除旧 scale 描述 |
| MongoDB 系列 | BSON `Double` -> `TapDouble`；`Decimal128` 不在范围；spec 应按 BSON Double 的非定点语义描述，框架仍遵循 source 属性优先 |
| Hive/Hudi/Paimon | `FLOAT` -> 32 bit，`DOUBLE` -> 64 bit；不得保留旧 `precision=7,scale=7` 或 `scale=15` 的定点描述 |
| Elasticsearch | `float` -> `TapFloat`，`double` -> `TapDouble`；`half_float`、`scaled_float` 进入显式 out-of-scope allowlist |
| Kafka Avro | Avro `float`/`double` 按协议分别为 `TapFloat`/`TapDouble` |
| Excel/通用 API/脚本连接器 | 必须以实际 SDK 返回类型为准；SDK `Float`/binary32 才映射 `TapFloat`，SDK `Double`/binary64 才映射 `TapDouble`；只凭展示名称不能自动判断 |
| Snowflake | `FLOAT` 是否为 binary64 需按当前 connector JDBC/官方定义确认；`DECFLOAT` 不纳入本次二进制浮点改造 |
| `SMALLFLOAT` 等 16 bit 或厂商专有类型 | 不强行映射为 `TapFloat`；先完成官方定义登记，超出 32/64 bit 范围时进入 allowlist 并阻止误归类 |

### 11.3 规范文件治理

- 只修改 `tapdata-connectors/**/src/main/resources/**` 和 `tapdata-connectors-enterprise/**/src/main/resources/**`。

- 每个修改条目登记：数据源版本、源类型别名、实际 bit/byte、有效位数、有限范围、特殊值、参数含义和官方链接。

## 12. 测试设计

### 12.1 公共 API 单测

覆盖：

- `TapFloat` 默认 bit=32、storageBytes=4、effectivePrecision=7、fixed=false；非空 source 配置覆盖默认值。
- `TapDouble` 默认 bit=64、storageBytes=8、effectivePrecision=15、fixed=false；非空 source 配置覆盖默认值。
- `TapFloat`、`TapDouble` 和 `TapCoefficientFloat` 均继承 `TapNumber`，但具体浮点 codec 由 `TapFloat`/`TapDouble` 的 Java 类型决定。
- 三者均返回 `TYPE_NUMBER=8`；具体 JSON 类型由 `typeName` 区分。
- clone 后具体类型、bit、范围、特殊值能力不丢失。
- `TapFloatValue` 输入 `1.234567890123d` 后值等于 `Double.valueOf(Float.valueOf(...))`。
- `TapDoubleValue` 保留 binary64。
- `Float`/`Double`/`BigDecimal` Java 推导正确。
- `FromTapFloatCodec` 返回 `Float`，`FromTapDoubleCodec` 返回 `Double`。

### 12.2 schema 兼容测试

- 新 JSON `type=8,typeName=TapFloat` -> `TapFloat`。
- 新 JSON `type=8,typeName=TapDouble` -> `TapDouble`。
- 新 JSON `type=8,typeName=TapNumber` -> `TapNumber`。
- 历史 JSON 只有 `type=8` -> `TapNumber`。
- 非法 `typeName` 报错。
- `typeName`/`type` 冲突记录 warning。
- Jackson 两个入口和 PDK Fastjson 入口行为一致。
- 新类型 clone、序列化和反序列化不丢失具体类型。

### 12.3 mapping 测试

- `TapFloatMapping` 只匹配/返回 `TapFloat`。
- `TapDoubleMapping` 只匹配/返回 `TapDouble`。
- `to=TapCoefficientFloat` 的 mapping 能根据 `coefficient` 区间把有效位数 p 解析为 `TapFloat` 或 `TapDouble`。
- MySQL `FLOAT(23)` -> `TapFloat`，`FLOAT(24)` -> `TapDouble`；SQL Server/PostgreSQL `FLOAT(24)` -> `TapFloat`，`FLOAT(25)` -> `TapDouble`。
- p 缺失时使用该 source mapping 已有的默认/优选 precision；p 缺失、越界、区间重叠或系数配置缺失时明确失败。
- `TapCoefficientFloatMapping` 解析后必须继续应用 source 的 bit/storageBytes/effectivePrecision/fixed 等属性。
- `TapNumberMapping` 仍保留旧兼容能力，不通过固定 bit 值或 scale 猜测单双精度。
- `TapFloat` -> `TapDouble` 允许 widening。
- `TapDouble` -> `TapFloat` warning/失败。

### 12.4 历史模型测试

- `TapNumber + SQL Server + dataType=float(53)` -> 内存 `TapDouble`。
- `TapNumber + SQL Server + dataType=real` -> 内存 `TapFloat`。
- `TapNumber + PostgreSQL + dataType=double precision` -> 内存 `TapDouble`。
- 缺少 connector/dataType 时保持 `TapNumber`。
- 无法生成确定 DDL 时返回 `LEGACY_FLOAT_TYPE_UNRESOLVED`。
- 不调用 source metadata、不重新加载模型定义。
- 规范化只执行一次，所有后续组件读取同一结果。

### 12.5 端到端测试

至少覆盖：

1. SQL Server `float(53)` -> StarRocks `DOUBLE`。
2. SQL Server `real`/`float(24)` -> StarRocks `FLOAT`。
3. PostgreSQL `real`/`double precision` -> Doris/StarRocks 对应类型。
4. MySQL `FLOAT`/`DOUBLE` -> Doris/StarRocks 对应类型。
5. BigQuery `FLOAT64` -> `TapDouble`。
6. MongoDB BSON `Double` -> `TapDouble`。
7. 含小数值读写后不被 `scale=0` 截断。
8. NaN/Infinity 按源端能力执行保留或失败。
9. 双精度到单精度有显式 warning/阻止。
10. 所有源码 spec 能成功加载，且实际浮点条目不再生成 `TapNumber`。

## 13. 静态质量门禁

新增一个独立的 spec 检查器，建议放在 `tapdata-connectors` 的 connector test/validation 模块中，核心伪代码：

~~~text
遍历两个连接器仓库的 src/main/resources/**/*.json
  解析 properties.realName、properties.id、dataTypes
  对每个 dataTypes 条目：
    识别名称、name 字段或官方登记表中的浮点候选
    如果为固定实际 binary32/binary64：
      要求 to=TapFloat 或 TapDouble 与官方定义一致
      校验 bit/storageBytes/effectivePrecision 的类型和值格式，但不在框架层固定其取值
    如果有效位数决定精度：
      要求 to=TapCoefficientFloat
      要求 coefficient 只包含 TapFloat/TapDouble 的合法、不重叠区间
      要求 source 表达式参数能够提供有效位数 p
    浮点 mapping：
      不得把 coefficient 或有效位数参数写成新的 TapNumber 属性
      不得把有效位数误写成 decimal scale
    out-of-scope 类型：
      必须命中 allowlist，并带 reason 和 officialUrl
失败输出：
  connector、spec path、source type、current/expected type、bit/byte、
  precision/scale 差异、官方来源、修复建议
~~~

门禁不能只检查 `to=TapNumber`，还必须检查“64 bit 却被写成单精度”和“32 bit 却写成双精度”等属性错误。

## 15. 风险和回滚

| 风险 | 处理 |
| --- | --- |
| 老服务不识别 `typeName` | 保留 `type=8`；老服务退化为 `TapNumber`，新语义要求消费端升级 |
| 旧代码用 `instanceof TapNumber` 表示所有数值 | 全量审查，旧定点判断只接受 `TapNumber` |
| 浮点值被错误当定点 | mapping/codec 不再根据 scale、bit 猜单双精度；源类型确有 `$scale` 参数时只按源表达式解析，不将其作为平台定点推断依据 |
| `TapFloat` 载入未经量化的 `Double` | codec、构造器和单测三处执行 binary32 量化 |
| 历史字段无法唯一恢复 | 保留 legacy；类型敏感操作返回 `LEGACY_FLOAT_TYPE_UNRESOLVED` |
| 历史数据已经丢失小数 | 明确不可恢复，不在 resolver 中伪造数据 |
| 某数据源名称含 FLOAT 但实际是 NUMBER/DECIMAL | 以官方物理定义为准，进入 `TapNumber` 或 allowlist |
| target/classes 被直接修改 | 门禁只扫描 `src/main/resources`，构建后验证产物 |
| source spec 之间复制错误 | 每个数据源独立计划步骤和独立验收记录 |
