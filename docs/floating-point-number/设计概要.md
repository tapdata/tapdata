# 浮点数单/双精度适配设计概要

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 关联需求 | [TAP-12568](https://tapdata.atlassian.net/browse/TAP-12568) |
| 设计范围 | 平台单精度/双精度二进制浮点数适配，以及各数据源 `spec.json` 浮点类型定义修复 |
| 不包含 | `DECIMAL`、`NUMBER`、`NUMERIC`、`Decimal128` 及其他非本次范围的数值类型改造 |
| 适用仓库 | `tapdata`、`tapdata-common-lib`、`tapdata-connectors`、`tapdata-connectors-enterprise` |
| 文档状态 | 设计概要 |

## 2. 背景与问题定义

当前平台使用 `TapNumber` 表达整数、定点数以及不同数据源的单/双精度浮点数。浮点数被转换为 `TapNumber` 后，会继续参与精度、scale、fixed、范围和目标类型推演，导致以下问题：

1. 单精度与双精度无法从平台类型层面区分，模型推演只能依据不稳定的 `bit`、`precision`、`scale` 和范围字段猜测。
2. 浮点类型的 `precision` 被误当作十进制定点数精度，`scale` 被误当作小数位数；浮点数因此可能被推演为 `DECIMAL(p, 0)`，直接丢失小数部分。
3. 不同数据源对同名类型的定义不同。例如 SQL Server 的 `float(n)` 中 `n` 是尾数的二进制位数，并且只对应两种实际存储格式；Oracle 的 `FLOAT(p)` 则是 `NUMBER` 子类型，并不是 `BINARY_FLOAT`。
4. 当前连接器 `spec.json` 中存在错误或不完整的位宽、有效位数、范围、`fixed`、`precision` 和 `scale` 描述。

典型故障是 SQL Server `float(53)` 被推演为 StarRocks `decimal(27,0)`，导致源数据的小数部分被截断。该问题不是单个连接器的类型映射问题，而是平台浮点数类型契约和数据源类型描述同时不准确造成的通用问题。

本次设计遵循以下原则：

> 数据源的类型名称不作为平台分类依据；以数据源官方定义的实际存储格式、有效位数、范围和参数语义为准。实际单精度浮点数统一使用 `TapFloat`，实际双精度浮点数统一使用 `TapDouble`。

### 2.1 本轮关注点与结论

本次更新将以下关注点作为设计约束，而不是留待后续补充的事项：

1. **类型层次不做伪继承。** `TapFloat`、`TapDouble` 与 `TapNumber` 是 `TapType` 下的直接业务类型；可选的 `TapFloatingPoint` 只能作为不参与 schema 序列化和类型恢复的内部抽象实现，不能挂在 `TapNumber` 下面。`TYPE_NUMBER=8` 仅保留协议分类兼容，不代表 Java 继承关系。
2. **浮点值统一以 `Double` 承载，但保留具体值对象。** `TapFloatValue` 和 `TapDoubleValue` 都使用 `Double` 作为入站值载体；前者必须先执行 binary32 量化，后者按 binary64 保存。两者是 `TapValue` 下的直接业务值类型，不继承 `TapNumberValue`。
3. **旧模型必须在新代码下可运行。** 历史 `tapType=TapNumber` 的字段不要求重新发现源端 schema 或重新加载模型定义；优先使用已有连接器、`dataType/pureDataType` 和修复后的本地 spec 在内存中唯一规范化，无法确定时保留 legacy `TapNumber` 路径，并对类型敏感操作显式报出未解析状态。
4. **`spec.json` 必须按官方实际类型修复。** 位宽、存储字节数、有效位数、范围、特殊值和参数语义必须与官方定义一致。64 位源类型被错误描述为单精度是必须修复的编码/规范缺陷，不构成新旧类型设计上的兼容分支；静态质量门禁应直接拒绝这类错误。
5. **本需求一次性交付完整闭环。** 公共类型、值对象、序列化兼容、历史模型规范化、codec/mapping、全量 `spec.json` 修复、静态检查和回归验收共同构成本次设计范围；后续实施顺序只是执行顺序，不代表功能分阶段或留下第二阶段尾项。

## 3. 目标与非目标

### 3.1 目标

- 在平台类型层面区分 `TapFloat` 与 `TapDouble`。
- 保留现有 `TapNumber` 对整数、定点数和其他未纳入本次范围数值类型的兼容能力。
- 修复公共与企业连接器中所有实际单/双精度浮点数的 `spec.json` 定义。
- 将物理位宽、存储字节数、有效十进制位数、二进制 precision、有限值范围和特殊值能力纳入可验证的类型描述。
- 让类型推演、字段类型匹配、Java/JDBC 类型转换、目标 DDL 生成和 schema 序列化都使用同一套单/双精度语义。
- 覆盖 TAP-12568 的 SQL Server → StarRocks 回归场景，并避免同类问题在其他数据源复现。

### 3.2 非目标

- 不改造 `DECIMAL`、`NUMBER`、`NUMERIC`、`MONEY` 或其他定点/精确数值类型的内部模型。
- 不引入任意精度浮点数。
- 不把所有名称包含 `FLOAT` 或 `DOUBLE` 的源类型都强制归类为二进制浮点。
- 不把 `precision/scale` 继续作为普通二进制浮点的十进制定点语义。
- 不在本需求中解决 `Decimal128`、Elasticsearch `scaled_float`、`half_float`、`BFloat16` 等其他数值格式。

## 4. 官方定义核对原则

### 4.1 平台统一属性含义

浮点类型的描述必须区分以下概念：

| 属性 | 含义 | 是否适用于普通二进制浮点 |
| --- | --- | --- |
| `bit` / `bitWidth` | 实际二进制存储宽度，统一按 bit 表达 | 是，单精度 32，双精度 64 |
| `storageBytes` | 实际存储字节数 | 是，单精度 4，双精度 8 |
| `effectivePrecision` | 官方文档给出的有效十进制有效位数或有效位数下限 | 是，但只能表示近似能力，不能当作 DECIMAL precision |
| `binaryPrecision` | 数据源声明的二进制 precision，例如 `float(p)` 的 `p` | 仅在数据源支持该参数时使用 |
| `value` / `minValue` / `maxValue` | 有限值范围；特殊值另行描述 | 是 |
| `fixed` | 是否为定点/固定小数位类型 | 普通二进制浮点必须为 `false` |
| `precision` | 定点/精确数值的十进制总有效位数 | 普通二进制浮点不使用 |
| `scale` | 定点/精确数值的小数位数 | 普通二进制浮点不使用 |

其中，`precision` 与 `scale` 仅保留给定点/精确数值类型。对于浮点数，建议在映射描述中新增或统一使用 `effectivePrecision`、`binaryPrecision` 和 `storageBytes`，避免复用现有 `TapNumberMapping` 的十进制字段。

### 4.2 平台类型基线

| 平台类型 | 物理格式 | 存储 | 有效十进制位数 | 有限值最大值 | 平台语义 |
| --- | --- | --- | --- | --- | --- |
| `TapFloat` | IEEE 754 binary32 或数据源等价的 32-bit single | 32 bit / 4 byte | 通常 6–7 位，必须以数据源官方表述为准 | 约 `3.4028235E+38` | 近似值、非定点、允许数据源支持的 NaN/Infinity |
| `TapDouble` | IEEE 754 binary64 或数据源等价的 64-bit double | 64 bit / 8 byte | 通常 15–17 位，必须以数据源官方表述为准 | 约 `1.7976931348623157E+308` | 近似值、非定点、允许数据源支持的 NaN/Infinity |

“有效十进制位数”只用于能力描述和类型推演的辅助信息，不能据此生成 `DECIMAL(effectivePrecision, scale)`。例如 PostgreSQL 官方分别将 `real` 描述为 4 字节、约 6 位精度，将 `double precision` 描述为 8 字节、约 15 位精度；这不意味着它们具有可配置的十进制 precision/scale。

参考：

- [PostgreSQL Numeric Types](https://www.postgresql.org/docs/17/datatype-numeric.html)
- [SQL Server float and real](https://learn.microsoft.com/en-us/sql/t-sql/data-types/float-and-real-transact-sql?view=sql-server-ver17)
- [Oracle Data Types](https://docs.oracle.com/en/database/oracle/oracle-database/21/sqlrf/Data-Types.html)
- [ClickHouse Float32/Float64](https://clickhouse.com/docs/reference/data-types/float)
- [StarRocks DOUBLE](https://docs.starrocks.io/docs/sql-reference/data-types/numeric/DOUBLE/)
- [Apache Doris Floating-Point Types](https://doris.apache.org/docs/4.x/sql-manual/basic-element/sql-data-types/numeric/FLOATING-POINT/)

## 5. 平台类型模型设计

### 5.1 类型层次

`TapFloat`、`TapDouble` 不继承 `TapNumber`。当前 `TapNumber` 包含 `precision`、`scale`、`fixed`、`unsigned`、`zerofill` 等整数/定点数语义；让浮点类型继承它，会使 `instanceof TapNumber`、旧 mapping 和旧 codec 继续把浮点类型当成定点数处理。

建议采用以下层次：

```text
TapType
├── TapNumber                         // 旧模型、整数、定点数和其他数值类型
├── TapFloat                          // 32 bit / 4 byte single
└── TapDouble                         // 64 bit / 8 byte double
```

如果两个浮点类型确实需要复用实现，可以增加一个只用于代码复用的抽象基类：

```text
TapType
├── TapNumber
└── TapFloatingPoint                  // 抽象实现类，不是业务 schema 类型
    ├── TapFloat
    └── TapDouble
```

`TapFloatingPoint` 不得继承 `TapNumber`，不得作为 `spec.json` 的最终类型，也不得作为 `TapType.getTapTypeClass(String)` 的业务恢复目标。

`TapFloat` 和 `TapDouble` 仍属于协议层面的数值类别，但“数值类别”和“Java 类继承关系”必须分离：

- `TapFloat` 固定表达 32-bit single，初始化 `bit=32`、`storageBytes=4`、`fixed=false`。
- `TapDouble` 固定表达 64-bit double，初始化 `bit=64`、`storageBytes=8`、`fixed=false`。
- 浮点实现（若采用内部抽象类，可命名为 `TapFloatingPoint`）提供 `effectivePrecision`、`binaryPrecision`、特殊值能力等浮点专有属性；这些属性不应回填到 `TapNumber` 的定点字段。
- 普通浮点类型不填充 `TapNumber.precision` 和 `TapNumber.scale`；兼容读取旧数据时可以读取，但不能将其重新解释为定点约束。
- `minValue/maxValue` 使用有限值边界；NaN、正负 Infinity 使用显式能力字段，不把它们伪装成普通范围值。
- `TapFloat`、`TapDouble` 可以继续返回 `TYPE_NUMBER=8`，表示协议层面的数值类别；这不表示它们继承 `TapNumber`。
- 新代码不得用 `instanceof TapNumber` 判断“所有数值类型”；需要区分旧 `TapNumber` 和新浮点类型。

### 5.2 类型序列化兼容

当前序列化使用数值型 `type=8` 表示 `TapNumber`。为避免历史 schema 无法读取，建议：

```json
{
  "type": 8,
  "typeName": "TapDouble",
  "bit": 64,
  "storageBytes": 8,
  "fixed": false,
  "effectivePrecision": 15,
  "minValue": "-1.7976931348623157E+308",
  "maxValue": "1.7976931348623157E+308"
}
```

兼容策略：

1. 新版本写入 `TapFloat`/`TapDouble` 时保留 `type=8`，同时写出 `typeName`。
2. 新版本读取包含 `typeName` 的 schema 时恢复具体子类型。
3. 读取历史只包含 `type=8`、没有 `typeName` 的 schema 时继续恢复为 `TapNumber`。
4. 旧版本读取新 schema 时会退化为 `TapNumber`，因此新类型语义真正生效前，相关 schema 消费端必须升级到支持 `typeName` 的版本。
5. 不能使用新的独立 type byte 替换 `TYPE_NUMBER=8`，避免现有过滤器、协议和历史数据整体失效。

需要同步修改两个现有自定义 `TapType` 反序列化入口，使其优先解析 `typeName`：

- `iengine/iengine-common/.../JSONUtil.java`
- `manager/tm-common/.../JsonUtil.java`

同时补充 `TapType.getTapTypeClass(String)` 对 `TapFloat`、`TapDouble` 的支持。`TapFloatingPoint` 如果作为内部抽象实现类存在，不作为可序列化的业务类型，也不作为 `spec.json` 的最终 `to` 类型。

### 5.2.1 历史模型兼容

旧模型中浮点字段的 `tapType` 可能已经持久化为 `TapNumber`。新代码必须支持这类模型在不重新发现源端 schema、不重新加载模型定义的情况下继续执行。

兼容处理分为“可安全规范化”和“legacy 保持”两条路径：

```text
旧字段 tapType=TapNumber
        │
        ├─ 有 source connector + dataType/pureDataType
        │  且可由修复后的官方 spec 唯一解析
        │       └── 仅在内存中转换为 TapFloat/TapDouble
        │
        └─ 缺少原始类型、连接器上下文或存在歧义
                └── 保持 TapNumber，走 legacy 兼容路径
```

新增 `LegacyTapTypeResolver`（名称可按实现调整），在模型初始化或字段首次使用时执行，要求如下：

1. 输入包括连接器身份、`TapField.dataType`、`TapField.pureDataType`、已有 `tapType` 和当前修复后的 source spec。
2. 不访问数据源、不重新发现表结构，只使用已持久化的模型信息和本地 spec 完成内存解析。
3. 新模型已经是 `TapFloat`/`TapDouble` 时直接保留，不重复推断。
4. 旧 `TapNumber` 只有在源类型能够唯一映射时才转换；不能仅依据旧 `bit`、`precision`、`scale`、`fixed` 猜测。
5. 无法判定时保留旧 `TapNumber`，使用旧 codec 和旧 mapping 兼容执行，并记录结构化告警。
6. 如果某个操作必须重新生成目标 DDL 或进行精确浮点类型推演，而旧字段无法确定单/双精度，则不得静默选择类型，应明确标记 `LEGACY_FLOAT_TYPE_UNRESOLVED` 并阻止该类型敏感操作。

类型判断优先级为：

```text
明确的 TapFloat/TapDouble
  > 连接器身份 + dataType/pureDataType + 修复后的官方 spec
  > 旧 TapNumber 的兼容语义
  > 不进行推断
```

例如旧模型中保存：

```text
tapType = TapNumber
dataType = float(53)
connector = SQL Server
```

新代码应在内存中解析为 `TapDouble`，从而使 TAP-12568 场景继续推演为 StarRocks `DOUBLE`，且不需要重新加载模型或访问 SQL Server 元数据。

如果旧模型只剩下 `tapType=TapNumber`，没有源类型和连接器上下文，则不存在可靠的信息可以恢复原来的单/双精度身份。此时只能保持 legacy 行为，不能伪造新的精度结论。

### 5.3 值对象和编解码

本需求一次性引入独立的浮点值对象，不把值对象改造留到后续：

- `TapFloatValue` 和 `TapDoubleValue` 均以 `Double` 作为 Java 底层值载体。
- `TapFloatValue` 的值必须先按 binary32 进行量化，再以 `doubleValue()` 无损扩展到 binary64 后保存；不能把未量化的任意 Double 直接放入 `TapFloatValue`。
- `TapDoubleValue` 直接保存 binary64 值。
- 两个值对象必须分别绑定 `TapFloat`、`TapDouble`，不能仅用一个 `TapNumberValue` 加字段标记替代。
- 新的浮点值对象不继承 `TapNumberValue`，避免 `instanceof TapNumberValue` 继续把浮点值识别为旧数值值对象；需要兼容旧消费者时通过公共值接口、适配器或显式转换完成。

建议的值对象关系如下：

```text
TapValue
├── TapNumberValue                      // 旧整数、定点数和其他数值类型，底层值为 Double
├── TapFloatValue                       // TapFloat + binary32 量化后的 Double
└── TapDoubleValue                      // TapDouble + binary64 Double
```

如果需要复用浮点值对象实现，可以增加不改变业务类型关系的内部抽象实现类 `TapFloatingPointValue`，但它应直接基于 `TapValue`，不能继承 `TapNumberValue`。不能通过未经检查的泛型转换把 Float 放入 `TapNumberValue<Double>`。

编解码必须依据具体值对象和 `TapType` 分派，而不能依据 `scale` 猜测：

- `TapFloat` 入站值经过 Float 语义规范化后以 `Double` 保存；出站到 Java/JDBC 或目标驱动时必须转换为 `Float`。
- `TapDouble` 入站和出站均使用 `Double`。
- 新增 `ToTapFloatCodec`、`FromTapFloatCodec`、`ToTapDoubleCodec`、`FromTapDoubleCodec`，并分别注册到对应值对象。
- 对 `TapFloat` 的 Number 输入统一执行“Number → Float → Double”转换；对 `TapDouble` 执行“Number → Double”转换。
- 对 String 输入，先按目标浮点类型解析并执行范围、NaN、Infinity 和溢出校验。
- 禁止再使用“`scale != 0` 且 bit=32 才返回 Float”的隐式判断。该判断会把类型语义与定点属性绑定，是当前错误的根源。
- `TapNumberValue` 的默认类型继续为旧 `TapNumber`；只有明确 schema 为 `TapFloat`/`TapDouble` 时，才创建对应的新值对象。

重点修改：

- `ToTapNumberCodec`、`FromTapNumberCodec`：继续服务旧 `TapNumber`，不再负责浮点类型判断。
- `ToTapFloatCodec`、`FromTapFloatCodec`：负责 binary32 量化、Float 出站和 NaN/Infinity 能力。
- `ToTapDoubleCodec`、`FromTapDoubleCodec`：负责 binary64 解析、Double 出站和 NaN/Infinity 能力。
- `JavaTypesToTapTypes`：`Float` → `TapFloat`，`Double` → `TapDouble`，`BigDecimal` 保持原有 `TapNumber` 定点语义。
- `TapDefaultCodecs`：保证 `Float`/`Double` 的 codec 注册与新类型匹配。

## 6. `spec.json` 映射设计

### 6.1 基本格式

普通、无参数的浮点类型应采用以下结构：

```json
{
  "float": {
    "to": "TapFloat",
    "bit": 32,
    "storageBytes": 4,
    "effectivePrecision": 7,
    "fixed": false,
    "value": ["-3.402823466E+38", "3.402823466E+38"],
    "specialValues": ["NaN", "Infinity", "-Infinity"]
  },
  "double": {
    "to": "TapDouble",
    "bit": 64,
    "storageBytes": 8,
    "effectivePrecision": 15,
    "fixed": false,
    "value": ["-1.7976931348623157E+308", "1.7976931348623157E+308"],
    "specialValues": ["NaN", "Infinity", "-Infinity"]
  }
}
```

字段约束：

- `to` 必须为 `TapFloat` 或 `TapDouble`，不得继续为 `TapNumber`。
- `bit` 表示 bit，不表示 byte；4 字节浮点必须写 `32`，8 字节浮点必须写 `64`。
- `storageBytes` 用于消除历史 `bit` 字段注释和配置的歧义。
- `fixed` 必须为 `false` 或省略，禁止写 `true`。
- 普通浮点定义不得设置 `scale`、`defaultScale`、`preferScale`。
- `precision`、`defaultPrecision`、`preferPrecision` 不再用于表达普通浮点的十进制定点约束；使用 `effectivePrecision`。
- `value` 推荐使用字符串，避免 JSON 解析器或 Java `Double` 读取超大边界时产生二次舍入。
- `specialValues` 只描述数据源实际支持的值；不应因为 IEEE 754 通常支持就强行写入源端不支持的能力。

### 6.2 参数化浮点类型

需要区分三类参数，不能统一解释为 `precision/scale`：

1. **二进制 precision**：例如 SQL Server/PostgreSQL `float(p)` 的 `p`，决定 single/double 的存储类别。
2. **源端显示或存储约束**：例如 MySQL `FLOAT(M,D)`，其中 `M,D` 会导致源端舍入或显示行为，但不是平台 `TapNumber.scale`。
3. **被忽略的语法参数**：例如 ClickHouse 的 `Float32(12, 4)`，官方定义会忽略这些参数。

建议增加浮点映射专用字段：

```json
{
  "float[($precision)]": {
    "resolver": "TapFloatingPoint",
    "resultTypes": ["TapFloat", "TapDouble"],
    "binaryPrecision": [1, 53],
    "defaultBinaryPrecision": 53,
    "singlePrecision": {"range": [1, 24], "to": "TapFloat"},
    "doublePrecision": {"range": [25, 53], "to": "TapDouble"}
  }
}
```

`TapFloatingPointMapping` 负责解析参数并返回具体的 `TapFloat` 或 `TapDouble`。如果数据源连接器已经在 JDBC/驱动层将参数归一化为实际类型，则可以直接配置两个静态映射，不必重复解析源端表达式。

### 6.3 类型推演规则

| 源类型 | 目标类型 | 行为 |
| --- | --- | --- |
| `TapFloat` → `TapFloat` | 同精度 | 允许直接映射 |
| `TapFloat` → `TapDouble` | 32 → 64 | 允许安全扩展，不增加有效信息但不降低精度 |
| `TapDouble` → `TapDouble` | 同精度 | 允许直接映射 |
| `TapDouble` → `TapFloat` | 64 → 32 | 默认禁止自动降精度；若用户强制选择，必须提示可能溢出/舍入 |
| `TapFloat`/`TapDouble` → `TapNumber` | 旧兼容 | 只作为旧版本兼容，不得作为新模型的默认结果 |
| 浮点 → `DECIMAL` | 不在本次设计 | 不新增或改变该转换策略 |

目标类型匹配时，`TapFloatMapping` 只能匹配 `TapFloat`，`TapDoubleMapping` 只能匹配 `TapDouble`。保留 `TapNumberMapping` 对子类的兼容读取，但需要降低其对浮点字段的默认匹配优先级，防止浮点再次匹配到定点规则。

当前已发现的典型错误包括：

- MySQL 系列普通 `float` 使用 `precision=[1,6]`、`scale=[0,6]`，普通 `double` 使用 `scale=[0,17]`。
- PostgreSQL 系列 `double precision` 缺少明确 64 bit 描述，仍使用十进制 scale。
- SQL Server 主规范中的 `real` 使用 `bit=4`，且 `float(n)` 没有按 24/25 边界分流。
- Oracle/OceanBase Oracle 的 `BINARY_FLOAT`、`BINARY_DOUBLE` 使用了 `scale=37/307` 等不适用于二进制浮点的字段。
- MongoDB 的 BSON `DOUBLE` 存在 `fixed=true` 或 `precision/scale` 误用。
- BigQuery `FLOAT64` 使用 `scale=[0,6]`。
- StarRocks 的 `float/double` 和 ClickHouse 的 `Float32/Float64` 仍全部指向 `TapNumber`。

## 9. 代码影响面

### 9.1 公共类型与 PDK

- `TapType`：类型名解析、序列化兼容和类型分类。
- `TapNumber`：抽取或兼容浮点公共属性，避免 `precision/scale` 继续承载浮点语义。
- 新增 `TapFloat`、`TapDouble`；如确有实现复用需要，可增加仅供内部复用的 `TapFloatingPoint`，但不作为业务 schema 类型。
- 新增 `TapFloatValue`、`TapDoubleValue`；如确有实现复用需要，可增加直接基于 `TapValue` 的内部 `TapFloatingPointValue`，底层值统一使用 `Double`，但通过具体值对象保留类型身份。
- `ToTapFloatCodec`、`FromTapFloatCodec`、`ToTapDoubleCodec`、`FromTapDoubleCodec`：分别负责单精度规范化和双精度转换。
- `TapNumberValue`、`ToTapNumberCodec`、`FromTapNumberCodec`：继续服务旧 `TapNumber`，不得再通过 `scale` 猜测浮点类型。
- 新增 `TapFloatingPointMapping`，以及静态 `TapFloatMapping`、`TapDoubleMapping` 或等价实现。
- `TapMapping.build`：支持新的 mapping 类型和参数化浮点映射。
- `JavaTypesToTapTypes`：修复 Java `Float`/`Double` 推导。
- `TapDefaultCodecs`：补充浮点类型的 codec 选择。
- `LegacyTapTypeResolver`：在不访问数据源、不重新加载模型定义的前提下，将可确定的历史 `TapNumber` 浮点字段规范化为 `TapFloat`/`TapDouble`；无法确定时保留 legacy 路径。

### 9.2 引擎、管理端和模型推演

需要检查并修改所有直接判断 `TapNumber`、`TYPE_NUMBER`、`scale` 或 `bit` 的代码：

- schema JSON 序列化/反序列化：`iengine-common/JSONUtil.java`、`tm-common/JsonUtil.java`。
- schema union、字段类型匹配、目标类型推演和 DDL 生成。
- `ConverterProvider`、`FieldTypeUtil`、`DataTypesHandler`、`CompareRecord` 等基于 `TapNumber` 做类型分派的组件。
- `default-data-types.json`、mapping 文档以及 CLI 类型处理逻辑。
- 所有使用 `instanceof TapNumber` 的代码：确认是“所有数值类型”判断，还是“整数/定点数”判断；后者必须排除 `TapFloat`/`TapDouble`。

历史模型执行时，字段类型解析必须在上述组件进入类型推演、codec 选择和目标 DDL 生成之前完成。不能让一部分组件看到旧 `TapNumber`、另一部分组件看到新 `TapFloat`/`TapDouble`。

### 9.3 兼容规则

- `TYPE_NUMBER=8` 保持不变。
- 旧 `TapNumber` 的 JSON、历史 schema 和已有连接器继续可读。
- 新 spec 不再产生新的浮点 `TapNumber`。
- 旧类型映射文件若无法识别 `TapFloat`/`TapDouble`，应使用 `LegacyTapTypeResolver`；无法确定具体类型时明确记录兼容告警，而不是静默选择新的浮点类型。
- 对已落库的历史 schema 不做静默持久化改写；可在运行内存中规范化。只有显式保存迁移结果时，才写出 `typeName`。
- 旧模型无法恢复单/双精度身份时，数据搬运可以继续走旧 `TapNumber` 兼容路径；涉及新目标 DDL 或精确浮点推演的操作必须标记 `LEGACY_FLOAT_TYPE_UNRESOLVED` 并阻止静默决策。

## 10. 测试与验收设计

### 10.1 公共类型单元测试

- `new TapFloat()` 的 bit、byte、范围和 `fixed` 属性正确。
- `new TapDouble()` 的 bit、byte、范围和 `fixed` 属性正确。
- `TapFloat`/`TapDouble` 的 clone、equals/序列化行为不丢失具体类型。
- 新 JSON 带 `typeName` 可以恢复子类型；旧 JSON 无 `typeName` 仍恢复为 `TapNumber`。
- `Float`、`Double`、`BigDecimal` 的 Java 类型推导分别得到 `TapFloat`、`TapDouble`、`TapNumber`。
- `TapFloat`、`TapDouble` 不属于 `TapNumber` 的 Java 子类，但仍返回 `TYPE_NUMBER=8`，协议分类和 Java 类型层次均符合预期。

### 10.2 mapping 与 spec 测试

- 所有源码 `spec.json` 可以被 `TapMapping.build` 成功加载。
- 普通浮点条目不再生成 `TapNumber`。
- 单精度条目必须为 `bit=32`，双精度条目必须为 `bit=64`。
- 普通浮点条目不包含 `scale` 或 `fixed=true`。
- SQL Server/PostgreSQL `float(24)` → `TapFloat`，`float(25)` → `TapDouble`，默认 `float` → `TapDouble`。
- MySQL `FLOAT(23)` → `TapFloat`，`FLOAT(24)` → `TapDouble`；`FLOAT(M,D)` 不把 D 写入逻辑 `scale`。
- ClickHouse 带参数的 `Float32/Float64` 忽略参数，不产生定点属性。
- Oracle `BINARY_FLOAT` → `TapFloat`，`BINARY_DOUBLE` → `TapDouble`，Oracle `FLOAT(p)` 不误归类为二进制浮点。

### 10.3 端到端回归

必须覆盖以下场景：

1. SQL Server `float(53)` → StarRocks `DOUBLE`，不能生成 `decimal(27,0)`。
2. SQL Server `float(24)`/`real` → StarRocks `FLOAT`。
3. SQL Server 双精度字段写入包含小数的值，读取和写入后小数部分不被 scale=0 截断。
4. PostgreSQL `real`/`double precision` → StarRocks/Doris 的对应浮点类型。
5. MySQL `FLOAT`/`DOUBLE` → StarRocks/Doris 的对应浮点类型。
6. MongoDB BSON Double → 目标双精度浮点，不因 `fixed` 或 `precision=309` 推演为定点类型。
7. NaN、Infinity、-Infinity：对源端支持的连接器验证读取、转换、写入和错误策略。
8. 双精度到单精度的降级必须产生明确警告或阻止，不得静默截断。

### 10.4 历史模型兼容回归

必须覆盖“不重新发现源端 schema、不重新加载模型定义”的旧模型执行场景：

1. 历史 JSON 中只有 `type=8` 的 `TapNumber` 可以正常反序列化。
2. 历史字段 `TapNumber + dataType=float(53) + SQL Server` 可以由 `LegacyTapTypeResolver` 在内存中转换为 `TapDouble`。
3. 历史字段 `TapNumber + dataType=real + SQL Server/PostgreSQL` 可以在内存中转换为 `TapFloat`。
4. 历史字段缺少 `dataType`、`pureDataType` 或连接器上下文时，保持 `TapNumber` legacy 路径，不抛异常、不猜测精度。
5. 旧模型经过内存规范化后，类型推演、codec 选择和目标 DDL 生成不能出现部分组件使用旧 `TapNumber`、部分组件使用新浮点类型的混合状态。
6. 无法确定单/双精度且需要新目标 DDL 或精确推演时，返回 `LEGACY_FLOAT_TYPE_UNRESOLVED`，不得静默选择 `TapFloat` 或 `TapDouble`。
7. 旧缓存中的 `TapNumberValue` 可以依据已规范化的字段类型转换为新的浮点值对象；已经在历史链路中丢失的小数部分不得被宣称为可恢复。

## 11. 自动化质量门禁

建议增加一个独立的 spec 静态检查任务，在连接器构建或 CI 中执行：

```text
for each canonical spec under */src/main/resources:
  find dataTypes whose name or key matches float/double/real/binary_float/binary_double
  verify actual source definition against the official-source registry
  reject actual single/double definitions with to=TapNumber
  reject TapFloat with bit != 32 or TapDouble with bit != 64
  reject ordinary floating definitions with scale/defaultScale/preferScale
  reject ordinary floating definitions with fixed=true
  reject any source mapping that converts binary precision into decimal scale
  require explicit allowlist and explanation for out-of-scope types
```

检查结果至少输出：连接器、spec 文件、源类型、当前 `to`、期望 `to`、当前/期望 bit、precision/scale 差异、官方链接和修复状态。这样可以防止只修复 TAP-12568 相关连接器而遗漏其他数据源。

## 13. 风险与决策记录

| 风险 | 处理方案 |
| --- | --- |
| 旧服务无法理解 `TapFloat`/`TapDouble` | 保留 `type=8` 和旧 JSON 读取；发布说明明确新语义需要升级消费端 |
| 现有代码用 `instanceof TapNumber` 表示定点数 | 全量审查并将“数值类型判断”和“整数/定点数判断”拆开 |
| 数据源文档对有效位数表述不同 | 保留源端原文语义，平台统一物理格式，`effectivePrecision` 只作能力信息，不参与 scale 推演 |
| 参数化类型无法用一个静态 mapping 表达 | 引入 `TapFloatingPointMapping` 按 binary precision 解析并返回具体子类型 |
| 目标端只支持单精度 | 双精度到单精度默认阻止或显式告警，不静默降级 |
| `value` 超出 JSON/Double 精确表示范围 | spec 中使用字符串表示边界，由 mapping 解析为 `BigDecimal` |
| 连接器目录存在重复的 `target/classes` 规范 | 只修改 `src/main/resources`，构建后重新生成产物 |
| 历史模型的浮点字段只有 `TapNumber` | 依据连接器身份和 `dataType/pureDataType` 在内存中解析；无法确定时保留 legacy 路径，不从旧数值属性猜测 |
| 历史缓存值已经被错误截断 | 类型规范化只能修复后续读取和转换，不能恢复已经丢失的小数信息 |
| 旧模型被不同组件以不同类型解释 | 在类型推演、codec、DDL 之前统一执行 `LegacyTapTypeResolver`，并缓存本次运行的规范化结果 |

最终验收标准是：平台内部新发现或可安全规范化的实际单精度浮点均为 `TapFloat`，实际双精度浮点均为 `TapDouble`；普通二进制浮点不再携带错误的十进制定点 `scale` 语义；历史模型在无需重新发现源端 schema 的前提下能够继续运行；TAP-12568 场景中的 `float(53)` 能稳定推演为目标 `DOUBLE`，且后续读取和写入不丢失源数据小数部分。
