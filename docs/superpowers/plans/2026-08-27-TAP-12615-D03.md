# TAP-12615 D03 Recovery Task Lock Implementation Plan

> For agentic workers: REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task with review checkpoints.

Goal: Add an atomic, lease-based task lock so one task can have only one active DQL recovery batch and stale locks can be reclaimed.

Architecture: Store one lock document per task in dql_recovery_locks with a unique task_id index. Acquire with an expiry-aware Mongo findAndModify plus duplicate-key handling for the absent-document race; release by matching task and batch ownership. Integrate acquisition before batch creation and release on pre-dispatch compensation and terminal callbacks, while leaving D04 event transactions and D08 timeout scanning to their own steps.

Tech Stack: Java 17, Spring Data MongoDB, Maven multi-module build, JUnit 5, Mockito, existing TM DQL repositories and BizException error mapping.

Spec: docs/superpowers/specs/2026-08-27-TAP-12615-D03-recovery-task-lock-design.md

## Global Constraints

- The lock collection is dql_recovery_locks and task_id has a unique index named uk_task_id.
- The lock lease is 1800 seconds, matching dql.recovery.batchTimeoutSeconds=1800.
- Acquisition is authoritative in start; the preview active-batch read remains advisory only.
- Lock ownership is released with task_id + batch_id; an old batch must not release a reclaimed lock.
- D04 event transaction semantics, D05 message DTO changes, D06/D07 callback state machine changes, and D08 timeout scheduler are out of scope.
- Each step uses TDD: write a failing test, observe the expected failure, implement the minimum behavior, and rerun focused plus regression tests.
- Create one local commit with message prefix feat(TAP-12615): and do not push.
