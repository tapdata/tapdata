# TAP-12615 C07 Target Write Capture Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task with review checkpoints.

**Goal:** Integrate the C04-C06 DQL classification, Storm Guard, payload/identity builders, and TM event reporter into the existing target write split-and-skip flow.

**Architecture:** Keep `SkipErrorEventAspectTask` as the target-write capture boundary. Classify the batch failure before deciding whether to split, classify each single-record failure again after splitting, and make a record skippable only after a successful `DqlEventReporter` acknowledgement. Preserve the existing `SkipData` feature gate until the later F05 independent DQL configuration is available.

**Tech Stack:** Java 17, Maven multi-module build, JUnit 5, Mockito, existing Tapdata aspect/task APIs, C04-C06 classes in `iengine-common`.

**Spec:** `doc/TAP-12615-DLQ-controlled-reprocessing-detailed-design.md`, section 8.1; `doc/TAP-12615-DLQ-controlled-reprocessing-development-plan.md`, C07 row.

## Global Constraints

- Shared connection/network/target availability failures must remain in the existing task retry/error path and must not be split into many DQL records.
- Only `RECORD_DLQ` may call the event reporter and return a skipped record.
- A failed or unavailable TM report must not be treated as a skipped record; the candidate skip metric must be rolled back.
- Use the existing `SkipData` configuration as the current capture gate; do not add the later F05 DQL configuration in C07.
- Do not implement processor-node capture, record-success callbacks, replay workers, or new metrics in C07.
- Create one local commit with message prefix `feat(TAP-12615): ` and do not push it.

### Task 2: Implement C07 target-write capture

**Files:**
- Modify: `iengine/modules/skip-error-event-module/src/main/java/io/tapdata/task/skiperrorevent/SkipErrorEventAspectTask.java`

**Interfaces:**
- Consumes: `DqlExceptionClassifier.classify`, `DlqStormGuard.protect`, `DqlPayloadSerializer.serialize`, `DqlPayloadPreviewBuilder.build`, `DqlEventIdentityGenerator.generate`, and `DqlEventReporter.report`.
- Produces: target-write behavior where only an acknowledged `RECORD_DLQ` event is skipped.

- [x] **Step 1: Add DQL dependencies and task context construction**

Add classifier, Storm Guard, payload serializer/preview/identity generator, and optional reporter fields. Construct the reporter from an `HttpClientMongoOperator` during task startup. Keep a missing reporter fail-closed: a record classified as `RECORD_DLQ` must throw `DqlEventReportException` instead of being skipped.

- [x] **Step 2: Replace the batch failure gate with shared-failure classification**

Build a target-write `DqlClassificationContext` with `DqlBatchContext.batchFailure(...)` and the current task snapshot. Throw the original batch exception for system/shared/protected decisions. Preserve the existing split path for a batch exception that remains eligible for record isolation.

- [x] **Step 3: Reclassify each single-record failure**

For each failed single record, classify with `DqlBatchContext.singleRecord()`. Apply Storm Guard only for `UNKNOWN`, then return `true` only for `RECORD_DLQ`; otherwise propagate the original failure so task retry/error handling remains authoritative.

- [x] **Step 4: Build and report the DQL event before committing the skip**

Build a `DqlEventReport` from task/table/event metadata. Apply the classification and identity metadata, attach the bounded payload snapshot plus sanitized preview, and call `DqlEventReporter.report(taskId, report)`. Increment the candidate skip count only for limit evaluation; decrement it for a rejected limit or failed report. Call `logSkipEvent` only after report acknowledgement.
